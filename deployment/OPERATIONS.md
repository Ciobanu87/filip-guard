# Authorized infrastructure setup — not deployed

All code stays on `filip-guard-development`. Production AutoFix remains blocked.
This runbook configures existing components; it does not provision accounts,
activate subscriptions, send mail, install services or generate production keys.

## Provider choice and cost limits

**Backblaze B2 private S3 bucket** matches the existing SDK adapter. Its published
free allowance starts with 10 GB. Use a private bucket in the authorized account
region and a bucket-scoped application key restricted to required read/write
operations, without deletion/admin permissions. Never use a master account key.
Private backups do not need a public bucket. Provider caps/alerts must be set
before live writes; account usage, old object versions and download allowance
must be monitored. Do not add billing or authorize overages. Reaching a quota
must block repair instead of bypassing backup. No bucket or live credentials are
configured here. External provider recovery is **not yet validated**.

**Brevo free transactional SMTP** matches the existing verified TLS adapter:
`smtp-relay.brevo.com:587`, STARTTLS, provider SMTP login and SMTP key (not an API
key). Published free allowance: 300 messages/day. The deployment reserves at most
300 attempts/day in SQLite, including uncertain sends, across workers/restarts.
This cap does not cover other apps sharing the provider account. Account/domain
approval, authenticated sender and verified recipient consent remain prerequisites.
No actual Brevo message has been sent by the tests.

Official references (reviewed 2026-11-24):

- https://www.backblaze.com/docs/en/cloud-storage-get-started-with-a-backblaze-integration
- https://postman.backblaze.com/

## Host and persistent state

An explicitly authorized always-on Linux host and persistent private volume are
still required. No free host with guaranteed persistent SQLite storage and a
continuous worker has been provisioned. An ephemeral/sleeping free UI host or
stateless scheduled GitHub Actions runner is insufficient for this architecture.
Do not move journals, schedules, session databases or email quota to temporary
storage just to claim zero hosting cost.

The UI and worker must share `FG_CUSTOMER_AUTH_DB`, `FG_CUSTOMER_DATA_ROOT` and
`FG_MONITOR_DB` on a local persistent filesystem with SQLite locking (not a
shared network filesystem). Keep directories 0700, files 0600, and independently
back up the application metadata on encrypted operator-controlled storage. An
archive of WordPress content is not a backup of the accounts, journals, receipts,
schedules, notifications, WordPress installation or full database. For a complete
application recovery drill, quiesce UI/workers before a consistent encrypted
volume snapshot, restore it on an isolated host, then reconcile uncertain writes
before resuming. This host-level recovery remains unvalidated.

`guard-test.service.example`, `monitoring-paths.env.example`,
`test-workspace.env.example`, `email-worker.conf.example` and the existing
`../monitoring-worker.service.example` are templates only. Review user/paths and
private TLS ingress on the authorized host before installing. They do not run by
being committed. UI origin/test flags remain disabled in the template. The
monitoring worker receives no WordPress master keys and performs read-only scans.
Its leases, journals and rate limits remain the existing implementations.

Start the worker with `python monitoring_worker.py --once` for a bounded check,
then supervise `python monitoring_worker.py`. Restart it against the same paths;
durable leases fence abandoned work and preserve history. `worker_recent` and
the UI warning distinguish a configured schedule from an actually running worker.
Email configuration failure is reported without stopping read-only monitoring.
Systemd itself and host reboot behavior have not been validated on a deployed host.

## Secrets and key custody

Prefer the host's managed secret mounts / systemd `LoadCredential` files. Never
put secret values in GitHub, argv, environment templates or logs. Paths and key
version IDs are nonsecret. Keys must be externally generated/retained by the
operator: none are generated by application startup or these commands.

Set `FG_GUARD_KEY_DIRECTORY` to a private directory containing `v1.key`, `v2.key`,
etc., each exactly 32 binary bytes, mode 0600 or 0400. Set `FG_GUARD_KEY_ID` to the
active version. The directory must deny group/other access. The legacy single
`FG_GUARD_MASTER_KEY_FILE` still works for a single version, but cannot recover
multiple historical versions. Private files are opened without following final
symlinks; FIFOs/devices, public permissions, missing/short keys and invalid IDs
fail closed. Credential and backup subkeys remain HKDF-separated per customer/site.

Retain at least one separately protected, access-controlled recovery copy of all
needed key versions outside the application host and outside the content bucket.
Document who can recover them; test access independently. Losing a key cannot be
repaired by resetting a customer password. No remote KMS or key escrow is claimed.

Rotation procedure:
1. Mount the new externally retained version alongside old versions; verify the
   independent custody copy first. Add both versions to managed secret mounts.
2. Set the active key ID and restart the UI. New connections use that version.
3. For an existing owned site, run `python operations_keys.py --account ACCOUNT
   --site-id SITE_ID` on the authorized host with the shared paths/key mounts.
   It prompts for the FILIP GUARD account password privately, verifies ownership,
   re-encrypts credentials with a conditional update and logs out. It does not
   contact WordPress, change Application Passwords, delete archives or print keys.
4. Existing archives retain their original key IDs. Keep old versions until every
   retained archive and independently stored recovery copy has been recovered or
   safely migrated under a separately approved retention process. Merely changing
   the active key does not re-encrypt old archives or resolve key compromise.

## External backup verification and independent recovery

Supply explicit provider configuration only through the authorized host:
`FG_GUARD_S3_ENDPOINT`, `FG_GUARD_S3_BUCKET`, `FG_GUARD_S3_REGION`, and
`FG_GUARD_S3_CREDENTIALS_FILE` (private JSON with `access_key_id`,
`secret_access_key`, optional `session_token`). Region must match the provider.
The SDK never uses ambient/personal credential lookup. Construction alone does
not verify a provider connection.

After explicit authorization and cost-cap checks, run:

```
python operations_backup.py probe --authorized-external-access
```

This writes one encrypted **synthetic** object, uploads/downloads/decrypts it,
and restores into a new private database without the source database. Its test
key is ephemeral; it is not a production key. It leaves the synthetic object in
the provider bucket and never deletes data. A successful probe proves only this
provider path at that time, not full-site recovery or key custody.

Export a trusted receipt copy for an actual content backup to a new private file:

```
python operations_backup.py manifest --customer-id CUSTOMER_ID --site-id SITE_ID --backup-id BACKUP_UUID --destination /private/recovery.json
```

This reads the local owner binding and durable receipt without changing the
application database. Store the metadata separately under operator custody; it
contains no key. It records object ID, ciphertext digest, key version and scope.
It must be copied off the host; the command does not provision offsite custody.
On a fresh authorized host with only this trusted receipt copy, provider access
and retained key version, recover to a **new** destination:

```
python operations_backup.py recover --authorized-external-access --manifest /private/recovery.json --destination /private/recovered-content.sqlite
```

No Streamlit session, account database, original backup database or WordPress
write is required. The tool derives the original customer/site backup key,
verifies ciphertext SHA-256 and AES-GCM authentication, then validates SQLite
and every saved content hash. It refuses existing destinations. Recovery never
automatically writes content back to WordPress or bypasses approval/concurrency.
Test the real provider with retained production-version keys before launch; unit
tests cover this path using ephemeral keys and simulated object storage only.

## Email enablement and verification

Leave `FG_EMAIL_AUTHORIZED=0` until sending has been separately authorized.
Set `FG_SMTP_CREDENTIALS_FILE` to private JSON `{username, password}` containing
the provider SMTP login/key; `FG_SMTP_SENDER` must be the authenticated sender.
Mount `FG_EMAIL_BINDINGS_FILE` as a private JSON list of server-verified records:
`{customer_id, address, verified_at, consent: true, revoked: false}`. Records must
come from actual verification and consent; the file format does not verify an
address by itself. No customer addresses are inferred from notification payloads.
Per-send lookups observe revocation. Unverified/ambiguous/wrong-account bindings
are blocked. This is operator binding, not a newly invented customer email flow.

Only after domain/sender approval, DKIM and provider-recommended DNS checks,
provider quota verification, and explicit test-send authorization: enable SMTP
for an owned verified test mailbox, dispatch one due notification, check receipt,
headers, inbox/spam behavior and restart deduplication. Check bounce/complaint
handling with the provider; no webhook processing has been added. Lost SMTP
acknowledgments are quarantined as unknown, never automatically re-sent. A 250
acceptance is not proof of inbox delivery. Current tests mock SMTP connections;
no customer or real external mailbox has received a test message.

## Mandatory launch gate

- Real external encrypted backup upload/readback and independent recovery with
  retained keys/receipt metadata, including provider outage/quota failure.
- Independent key-custody/rotation drill and encrypted application-state recovery.
- Authorized persistent host reboot: UI, worker, leases, history and alerts survive.
- Provider/domain/consent validation and explicitly authorized owned-mailbox send;
  verify acceptance, delivery, quota and uncertain-send reconciliation.
- Latest offline + real WordPress/MySQL CI green; isolated end-to-end retest with
  the configured provider. Production AutoFix remains blocked pending separate approval.

No service account, billing, DNS, production infrastructure or customer site has
been changed by this preparation.
